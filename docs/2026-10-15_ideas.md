# Ideas — dreaming session, 2026-10-15

A capture page for upcoming-feature ideas. Nothing here is scheduled or being built. Ideas get promoted into the roadmap (`docs/2026-09-29_api-site-settings-findings.md` or a dedicated spec) only when we decide to, and that promotion happens in a later session.

Each idea gets a short shape: what it is, who it's for, why now, how it fits what already exists, and open questions. Rough is fine.

## Ideas

### 1. The SpinupTUI ecosystem: four modules and a station

**The observation.** SpinupTUI has quietly become the glue for a set of always-on tools built around it: an unattended incident watcher, a daily digest, an nginx config deploy pipeline, a job queue, and Telegram/Basecamp notifications. Each was built for one operator's fleet, and each leans on the same SpinupTUI primitives (`incidents`, `ssh-exec`, `siblings`, the monitor registry, the stored credentials). Packaged, they become a story a landing page can tell: the TUI is the cockpit, the modules are what keep watching after you close it.

**Who it's for.** A SpinupWP agency or freelancer with a fleet who has a machine that's always on (a spare Mac mini, a Linux NAS, a small VPS) and wants the fleet watched, defended and reported on without paying for another SaaS.

**Names** (decided 2026-10-15; see "Naming" below):

| Module | One line | Prior art that exists today |
|---|---|---|
| **Sentinel** | Watch the fleet, triage what breaks, write it up | An incidents watcher (`spinuptui incidents --all` diffed against state, a headless agent only on a new `down`), a watchdog for the watcher, a daily 08:00 digest, crawler-volume checks |
| **Samurai** | Defend a site at the nginx layer, proactively and in reaction to what Sentinel sees | The nginx-deploy pipeline (root-owned allowlist gate, `nginx -t`, auto-rollback) and its first snippets (`bot-block.conf`, `events-calendar-trap.conf`) |
| **Beacon** | Tell the right people: operator pager and client updates | Four separate Telegram senders in four places, plus a Markdown→Basecamp poster for client threads |
| **Scheduler** | Hand the station a job for later: "check this tomorrow at 8" | A git-as-queue job runner: jobs are Markdown files, one dispatcher every 5 minutes, reports committed back, digest to Telegram |

**How the pieces relate.** They aren't four peers; they form layers, and that shapes the build order:

- **Infrastructure:** Beacon (everything needs to talk) and Scheduler (everything needs to run unattended).
- **The headline:** Sentinel detects; Samurai responds. Sentinel's findings are Samurai's input, and Beacon is how a human approves Samurai's proposed actions.
- **Delivery:** station setup installs and wires all of the above on an always-on machine, then proves it works. It isn't a module; see "Station" below and idea 5.

**Design principles to carry through every module:**

- **SpinupTUI stays the single source of truth** for credentials, the fleet list, monitors and SSH access. Modules call `spinuptui …`; they never keep their own site list or token. That's already how the prior art works, and it's why it worked.
- **Deterministic first, agent optional.** The existing automation is careful about this: a cheap scripted check runs every tick and an agent wakes only for a real event. Follow-ups that post to clients use fixed templates, not generated text, so what gets posted is exactly what was reviewed. Packaged, the deterministic tier must stand alone and the AI-diagnosis tier should be bring-your-own-agent (Claude Code, Codex, …), per the tool-agnostic stance.
- **Public framework, private data.** The prior art already splits a tracked, shareable framework from gitignored per-site config (`*.conf.example` committed, real domains never). Keep that split as a hard rule.
- **Every write is gated.** Reading is free. Anything that changes production (an nginx rule, a client post) goes through confirm-before-firing, either interactively or as an approval request via Beacon.

#### Station (a concept, not a module)

Originally a fifth module called Playbook; retired as a product name on 2026-10-16 (see idea 5). A **station** is an always-on machine running SpinupTUI's modules unattended. **Station setup** is the guided run that makes one (`spinuptui station setup | status | doctor`).

A guided setup that turns a machine into a station: install Bun and `spinuptui`, add the token, attach existing Kuma monitors, generate an SSH keypair and grant it fleet-wide (the existing `K` grant-key flow), set up Beacon channels, install the schedules, then run a self-test that ends by sending a "station online" message. Ideally re-runnable as a `doctor` that reports drift.

Open questions:

- **Linux is the real test.** A Linux box such as a home NAS (often Ubuntu on older Intel hardware) is a likely station. Does OpenTUI's native library load on linux-x64? Can headless commands (`incidents`, `ssh-exec`) run without loading the renderer at all?
- **Secrets storage isn't cross-platform yet.** Sudo passwords live in the macOS Keychain. Linux needs `secret-tool`/libsecret, or an encrypted file, or simply no sudo on stations. This was already an open follow-up.
- **launchd vs systemd timers vs cron.** Station setup generates the right one per OS. Since Scheduler's dispatcher is the only OS unit (idea 4), this is Scheduler's job.
- **Who watches the watcher?** A station that dies silently is worse than none. Idea: station setup registers an Uptime Kuma *push* monitor as the station's heartbeat, so Kuma (already integrated) pages when the station goes quiet. That replaces the bespoke watchdog with something SpinupTUI already speaks.
- **Agent auth on a headless box.** The diagnosis tier needs a logged-in agent CLI. The prior art already detects an auth failure and pages for a re-login; Station setup should set that up and test it.

#### Sentinel

Package the incident watcher and daily digest as `spinuptui sentinel` (or similar): `sentinel run` (one tick), `sentinel digest`, `sentinel status`. The watched set comes from SpinupTUI's monitor registry, so no list needs maintaining.

What it would ship with:

- New-down detection with high-water-mark state (exists).
- A box-level triage step: run `siblings --probe` before blaming the paging domain (exists, and important; the paging domain is routinely not the cause).
- A daily digest (exists).
- **Expectation checks** (exist as one-offs, generalize them): "this crawler should hit this site at least N times a day", "this URL space should keep returning 410", "after this fix, measure the next 24h against the previous 24h". These are the most novel part. They catch silent failures that uptime monitoring never sees.
- Optional agent diagnosis that drafts an incident report in the existing format.

Open questions: where do incident reports live for a packaged user (a local directory, a git repo they choose)? How do expectation checks get declared (one config file per check type today, or one unified file)?

#### Samurai

Close the loop: Sentinel sees abuse in the access logs, and Samurai proposes (and with trust, applies) an nginx rule through the existing gated deploy. In effect, a local, fleet-aware bot fight mode that doesn't need Cloudflare.

**Reactive ideas** (triggered by Sentinel):

- **Time-boxed bans.** An IP, CIDR or user-agent over a request-rate threshold gets a `deny`/`return 444` with an expiry. Expiry is mandatory, so rules never accumulate. Since the gate never deletes, "expire" means rewriting the ban file without that entry.
- **Under-attack mode.** On a load spike, tighten `limit_req` on the expensive, uncacheable endpoints (`wp-login.php`, `xmlrpc.php`, `?s=` search, `wc-ajax`, `admin-ajax`, `/wp-json/`), then relax it automatically when load recovers.
- **Cache-busting defense.** Bots appending random query strings defeat FastCGI page cache and hit PHP on every request. Detect a high cache-MISS ratio on one path with junk params, then ignore unknown params in the cache key or 444 them.
- **Crawler-trap closing.** Infinite URL spaces (calendar date views, faceted filters, endless pagination) get a 410 or `limit_req`. This is the calendar-trap fix, generalized: detect the pattern, propose the snippet, then measure before and after automatically.
- **Scanner shutdown.** A burst of 404s for `.env`, `wp-config.php.bak`, `.git/`, or `phpinfo.php` means the IP is scanning, not browsing. Ban it.
- **Serve stale when PHP is drowning.** When PHP-FPM is saturated or Redis is down (the drop-in isn't graceful; a cache MISS becomes a 500), switch on `fastcgi_cache_use_stale` aggressively, or put a static "back shortly" page in front of uncached routes. Visitors get the last good page instead of an error.

**Proactive ideas** (a hardening pack, applied once per site):

- Block `xmlrpc.php` (unless Jetpack or the mobile app needs it), `?author=N` enumeration, `/wp-json/wp/v2/users` for anonymous visitors, PHP execution under `uploads/`, dotfiles, `readme.html`, `license.txt`.
- Security headers: HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and a CSP in report-only mode to start.
- `limit_req` zones on login and search as a permanent baseline, not just under attack.
- **A good-bot allowlist that Samurai must respect.** Verify Googlebot and Bingbot by reverse DNS, and never ban a crawler that Sentinel's expectation checks say the site depends on. This is the guard rail that stops the defense from killing ad revenue.
- **Drift detection.** Alert when SpinupWP has rewritten a managed file in a way that interacts with a custom override.
- **Rule hygiene.** Tag each custom rule so its hits are countable in the logs. The digest reports rules that haven't fired in 30 days as candidates to retire.

Open questions and hazards:

- **Real client IPs behind Cloudflare.** If a site is proxied and nginx doesn't trust Cloudflare's ranges via `set_real_ip_from`, every ban hits a Cloudflare edge IP and takes the site down for real visitors. Samurai must detect proxying (the DNS module already knows) and either fix real-IP handling first or push the rule to the Cloudflare WAF instead. Picking the right layer is part of the product.
- **Fleet scale requires the gate on every server.** nginx-deploy is per-site onboarding with a root install. SpinupTUI's privileged-SSH flow could do the install, but that's a big trust step to automate.
- **Autonomy ladder.** Default: propose via Beacon, and a human taps approve. Next: auto-apply for narrow, well-understood classes (scanner bans with a 24h TTL), always with a notice. Never: auto-apply open-ended rules.
- **Approval buttons (decided 2026-10-29): Approve, Refine, Ignore.** Every proposal carries an ID and a hash of exactly what it would apply. **Approve** applies that version only, after re-checking that the site is still in the state the proposal assumed, through the gated deploy. **Refine** prompts for a typed reply, and Samurai answers with a new proposal under a new ID; the old message's buttons go dead. **Ignore** closes the proposal with nothing applied. Taps are accepted only from the operator's own Telegram user, each button works once (the message is then edited to show the choice), proposals expire, and every proposal and tap is logged in `runs/`. The message shows the actual change and its rollback, not just a summary.
- Do SpinupWP's nginx builds include the geoip or real-ip modules? This needs checking before any geo or ASN rule is promised.

#### Beacon

One notification layer with two audiences that shouldn't be confused:

- **Operator channel** (pager): Telegram today, with Slack, ntfy, Pushover, email and a generic webhook as obvious adds. Short, actionable, can be noisy.
- **Client channel** (updates): Basecamp today (incident write-ups and follow-up numbers posted to the client's thread). Only reviewed or templated text, never raw agent output, and only through a confirm gate unless the template is pre-approved.

The immediate win is consolidation: one `spinuptui beacon send` replaces four Telegram senders, and every module uses it. The bigger idea is making it **two-way**. Telegram inline buttons (and Slack interactive messages) turn Beacon into the approval channel for Samurai ("Ban 203.0.113.0/24 on site X for 24h? [Approve] [Refine] [Ignore]"). That's what lets reactive defense work while the operator is away from a terminal. Inbound needs a listener on the station (Telegram long-polling avoids opening a port).

**Two-way Beacon (decided 2026-10-29).**

- **The listener is part of Beacon, not a module.** A module is named for what the operator gets from it; a listener gives nothing on its own. It's the return half of a conversation Beacon already owns, and how it receives depends on the channel (long-polling for Telegram, something else for Slack), so it lives with the channels.
- **Beacon owns the conversation; modules own what messages mean.** Beacon sends and receives, checks that a message or tap came from the operator's own Telegram user, records which updates it has handled so each is acted on once, and routes each command or tap to the module that registered it. Scheduler registers `/jobs`; Samurai later registers Approve / Refine / Ignore. Beacon carries no module-specific logic.
- **Always on.** The listener is a resident process with its own LaunchAgent that macOS restarts if it dies, installed and removed from the Modules tab like Scheduler. It long-polls (about one request a minute when idle, tens of MB of memory). Listening only for a few minutes after each proposal was considered and dropped: it needs a window that restarts on every Refine, a lock so two windows can't both poll, and Scheduler's tick as a fallback for late taps. Always-on needs none of that, and answers in seconds. It is a second OS-level unit beside Scheduler's dispatcher, an exception to "one clock" that is consistent with its intent: the listener does no scheduled work, it only waits for the operator.
- **What always-on costs to build.** The Scheduler tick checks the listener is alive and pages through Beacon if it isn't. Upgrading SpinupTUI restarts it, so it doesn't keep running old code. Telegram allows one consumer of a bot's updates, so Beacon setup's chat discovery pauses the listener or asks it for the chat instead of polling alongside it.
- **`/jobs` is the first command, before Samurai.** It replies with the station's scheduled jobs and their expiry dates, flagging any that expire soon, with an "Extend 1 year" button on those. It is read-only apart from that extension, so the inbound path (identity check, handled-once, routing, button taps) is proven on something harmless before it gates production writes.
- **The name stays Beacon.** A beacon signals one way, but to the operator it reads as "Beacon pages you, and you can answer." Renaming would also break callers that check for `spinuptui beacon send`.

Open questions: is per-site routing needed (which client thread, which Slack channel)? Is this per-site config in SpinupTUI, maybe alongside the existing monitor settings?

#### Scheduler

A queue of one-off and recurring jobs for the station, addable from anywhere: "verify the 410s are still holding tomorrow at 8", "post the before/after numbers to the client the morning after the fix", "re-run this audit weekly". Git is the queue, reports are committed back, and a digest goes out via Beacon.

The tension: the prior art is completely general-purpose and has nothing SpinupWP-specific. On a SpinupTUI landing page it should be framed by outcome, not mechanism ("follow-ups": the fix you shipped today gets checked tomorrow without you remembering). Under the hood it's also the engine that runs Sentinel's ticks and Samurai's expiries. Maybe it's less a module than the station's clock, presented as follow-ups.

**Blocked jobs and Run again (decided 2026-10-30, ships with Sentinel in 1.3.0-alpha.5).** The first real failure of an unattended agent job showed two gaps. An expired login stopped a report, and the agent said so clearly in its summary, but it exited normally, so Scheduler recorded `ok` for a run that did none of its work. And fixing the cause and retrying needed a terminal, though the page had arrived on a phone.

- **A job can say it's blocked.** `blocked` means the job ran but couldn't do its work because of something outside it, and it needs a person: a lapsed login, a missing permission, a service refusing it. It's different from `failed`, where the job itself went wrong. An agent ends its report with a line like `STATUS: blocked`, and a script exits with a reserved code. Scheduler adds the instruction to every agent job, so a job's prompt doesn't have to carry it. The exact marker and exit code are settled at build time.
- **`blocked` shows everywhere a status does:** the page, the report's title, `scheduler list`, `/jobs` and the Modules tab. A blocked run isn't counted as done, so a one-shot stays visibly unfinished until it succeeds or expires. Whether it retries by itself is left open; the first version waits for the operator, because a person usually has to fix the cause first.
- **Run again, from the pager.** The page for a failed or blocked job gets a **Run again** button, and `/jobs` shows the same button on those jobs. It's a Scheduler action on Beacon's one-use buttons: the operator fixes the cause, taps, and the result arrives on the same phone. The CLI equivalent, `scheduler run <id>`, already exists.
- **A tap never adds permissions.** Run again re-runs the job exactly as written, with the same allow list and sandbox. Job permissions stay decided at queue time, in a session where someone can read them.
- **Sentinel uses the same status.** A diagnosis or digest job that can't reach what it needs reports `blocked` through the same path, so Sentinel doesn't invent its own.

Building this means page sends need buttons, which Beacon's replies have and `beacon send` doesn't. Buttons are stored by the listener, so with no listener installed, a page goes out without them.

Open questions: how much of the existing runner generalizes (it assumes a specific agent CLI and a git remote)? Do we want a SpinupTUI-native job type, like "run this `spinuptui` command and report"?

#### Naming

Decided 2026-10-15: keep the original names, **Sentinel, Samurai, Beacon, Scheduler**. Alternatives were considered (Outpost, Rampart/Portcullis, Rota) and declined. Playbook was the fifth name until 2026-10-16, when it was retired in favor of "station" as a concept (idea 5). "Playbook" stays free for the diagnostics workflow and as our internal shorthand for this design work.

#### Suggested order, if and when promoted

Revised 2026-10-16 (see idea 4 for the reasoning):

1. **Beacon:** smallest, consolidates four duplicate senders, and every other module needs it.
2. **Scheduler:** the station's clock. Every other module's recurring work runs as a job inside it.
3. **Sentinel:** the headline feature, running on Scheduler and alerting through Beacon.
4. **Samurai:** last of the four, because it's the only module that writes to production on its own. The proactive hardening pack could ship earlier as a standalone, human-driven feature.
5. **Station setup:** assembles the four on a fresh machine. Only worth building once there's something to install. Linux station support is its own research spike.

#### The landing page itself

A one-pager: the pitch, a screenshot gallery (already exists), then the four modules as cards, plus a "Runs headless" section (not a fifth card): put SpinupTUI on any always-on machine, set it up as a station, and walk away. Until a module ships, its card says "coming" or the page leaves it out. A page listing four unbuilt products reads as vaporware. A page with the TUI plus Sentinel (live) and the rest teased reads as momentum.

### 2. Design sketch: Modules mode, with station setup as the preset

**The idea.** A Modules screen inside SpinupTUI that explains each module and installs it. Station setup runs the complete setup for headless, always-on operation.

#### The screen

One card per module (Sentinel, Samurai, Beacon, Scheduler), each showing:

- **What it does**, in outcome language. The same copy feeds the landing page's module cards, so the app and the site never drift. Write it once, use it twice.
- **Status on this machine:** not installed, installed and running, last run, unhealthy (with the reason), or "runs on another station" (see below).
- **Dependencies:** Samurai needs Sentinel and Beacon, and Sentinel needs Beacon to be useful. Installing a module offers to bring its dependencies along.
- **Actions:** install, configure, test, pause, uninstall.

The screen doubles as discovery. Discoverability is the main adoption risk, so the place you learn what a module does should be the place you turn it on.

**Station setup isn't a fifth card; it's the shortcut above the cards.** Installing modules one at a time is for someone adding Beacon to their laptop. "Set up this machine as a station" turns on all four in dependency order, and each module brings its own setup steps (idea 5). That keeps the mental model simple: modules are features, and a station is a machine that runs them unattended.

#### What "install" means

Modules ship inside the `spinuptui` package, so installing one downloads nothing. It writes three kinds of things, all of them listed before anything happens:

1. **Config:** a module section in the existing config, plus secrets (a Beacon bot token, for example) in the platform's secret store.
2. **Schedules:** jobs registered with Scheduler, not OS units of their own (see idea 4). The only OS-native unit on a station is Scheduler's dispatcher: a launchd LaunchAgent on macOS, a systemd user timer on Linux, calling the global `spinuptui` binary, never a path into a checkout.
3. **State:** a module directory for high-water marks, run logs and reports.

Rules carried over from the rest of the app: show a plan and confirm before applying (the same confirm-before-firing overlay the write actions use). Make it idempotent, so re-running repairs instead of duplicating. Make uninstall complete: it removes units and state and leaves config only if asked. Every TUI action also gets a CLI form (`spinuptui modules install sentinel --plan|--apply`, `spinuptui station setup --plan|--apply`, JSON to stdout), matching the existing pull commands. That lets an agent or a provisioning script set up a station without a TUI.

#### What station setup checks beyond the modules

The host checks no single module owns, each reported as pass, fixable, or needs-a-human:

- **Stays awake:** sleep disabled; on Linux, `loginctl enable-linger` so user timers run with nobody logged in.
- **Comes back after a power cut.** On macOS, LaunchAgents need a GUI login, and with FileVault a reboot stops at the unlock screen until someone types the password. Station setup can't fix that, but it must say so clearly and explain the options (auto-login, accept manual unlock, or a KVM).
- **Finds its tools unattended.** Schedulers start with a bare PATH, and a working interactive shell proves nothing about a launchd run. Station setup writes the PATH into the unit and tests it by running a real tick through the scheduler itself, not from the shell.
- **SSH reach:** generate the station's own keypair and grant it fleet-wide through the existing `K` flow, then confirm with one `ssh-exec` per server.
- **Agent tier (optional):** detect a logged-in agent CLI for Sentinel's diagnosis tier; skip cleanly if there isn't one.
- **Heartbeat:** register an Uptime Kuma push monitor for the station, so a dead station pages through the same monitoring that's already there.
- **Updates:** choose whether the station updates itself (off, patch only, or everything). A station running the global release means a bad release reaches it unattended, so the default should be conservative.
- **Proof:** finish with a full self-test that runs a Sentinel tick through the real scheduler and ends with a Beacon "station online" message. Setup isn't done until that message arrives.

#### Station setup runs in isolation, on the station

Decided 2026-10-15: station setup prepares the machine it runs on, from nothing, with no dependency on another configured SpinupTUI install. The flow is: (1) install SpinupTUI on the station, (2) SSH into it and run `spinuptui`, (3) turn on and configure modules there. (An earlier draft assumed a "station bundle" exported from a workstation; that's dropped. At most it's a later convenience for someone who already has a configured laptop.)

**What a fresh station needs, and where each piece comes from:**

| Need | Source in isolation | Notes |
|---|---|---|
| SpinupWP API token | Pasted at first run, or `SPINUPWP_ACCESS_TOKEN` | The normal first-run flow already handles this |
| Uptime Kuma connection | URL and credentials pasted | Already supported |
| **Kuma monitor registry** | **Rebuilt from Kuma itself** | The real gap. SpinupTUI keeps each domain's monitor IDs and push tokens in its *local* config, and `incidents --all` reads that registry. On a fresh install it's empty, so Sentinel would watch nothing. Fix: attach existing monitors from Kuma. See idea 3. |
| SSH access to the fleet | **One human step outside the box** | Chicken-and-egg: the `K` grant flow needs SSH access, and a new key has none. Station setup generates the station's key, shows the public half, says exactly where to add it in the SpinupWP dashboard, then waits and verifies with one `ssh-exec` per server. The newer site-user SSH-key API might automate this, but it's untested and may replace a site's key set rather than add to it. |
| Sudo passwords | Not needed for Sentinel | Sentinel reads as the site user. Only Samurai's one-time gate install needs sudo, and that can be prompted then. |
| Beacon credentials | Bot token and chat ID pasted | Beacon sends a test message before accepting them |

#### TUI, CLI, or both?

Both, with the CLI underneath. `spinuptui station setup` is the engine: an interactive guided run by default, `--plan`/`--apply` and flags for unattended or agent-driven setup. The Modules screen is a front end over the same steps: the place that explains each module, shows status, and calls the engine. That ordering hedges the open question of whether the TUI runs on a headless Linux station. If it does, step 2 above is the TUI. If it doesn't, the same setup still works through the guided CLI and nothing is lost but polish. Dropping the TUI entirely would lose the "explains the features" half of the idea, which is the discoverability win.

#### One station, many workstations

Once there is a station, the same Modules screen on a laptop should show "Sentinel runs on *station-name*, last heartbeat 3 min ago" rather than offering to install it again. Two machines both running Sentinel would double-page every incident. Kuma's push-monitor heartbeat is a ready-made shared record of where each module runs, with nothing new to host. The laptop still has a role: it's where you configure Beacon routing, approve Samurai proposals, and queue Scheduler follow-ups.

#### Open questions

- Which key opens Modules mode, and is it a route (like Servers or Sites) or an overlay? A route seems right, since it's a place you spend time.
- Does the TUI run on a headless Linux station at all? This is the same OpenTUI linux-x64 question as before. If not, the guided CLI carries the station.
- Where do secrets live on Linux (libsecret needs a session bus that a headless box may not have; an encrypted file may be the pragmatic answer)?
- How reliably can Kuma monitors be matched back to domains by name alone? Monitors created outside SpinupTUI won't follow its naming convention.
- Uninstall versus pause: pause is probably the common need (stop Sentinel during maintenance without losing state).

### 3. Sentinel and Uptime Kuma: attach what exists, bootstrap what doesn't

Two starting points for a new station, both of which Sentinel should handle: there's already a Kuma instance with monitors (attach), or there's no Kuma at all (bootstrap).

#### Attach: adopt an existing Kuma's monitors

**Why it's needed.** SpinupTUI keeps each domain's monitor IDs and push tokens in its *local* config (`kumaMonitors`), and `incidents --all` reads that, not Kuma. A fresh install connected to a Kuma full of monitors still sees none of them.

**Why it's tractable.** SpinupTUI already names every monitor it creates by a fixed convention, and registration already adopts same-named monitors instead of duplicating them:

| Kind | Kuma monitor name |
|---|---|
| Health / homepage | `{domain}` |
| Load push (vanity) | `{domain} load` |
| Redis sentinel | `{domain} redis` |
| PHP-fatal sentinel | `{domain} php-fatal` |
| Front-page fingerprint | `{domain} front page` |
| Cache bypass | `{domain} cache-bypass` |

Kuma's monitor list also carries each push monitor's `pushToken`, and the fingerprint monitor's keyword, so nearly the whole local registry can be rebuilt from Kuma alone. Only the fingerprint's calibration notes (`kind`, `detail`, `derivedAt`) are lost, and those are display-only.

**The flow** (a Sentinel step, run during station setup, and also useful on any second workstation):

1. Connect to Kuma and list every monitor; list every site in the fleet.
2. **Exact matches** (by the naming convention) are attached automatically.
3. **Likely matches:** a hand-made monitor whose URL host is a fleet domain (or `www.` of one) but whose name doesn't follow the convention. Show these for a yes/no.
4. **Leftovers, both ways:** fleet sites with no monitor (offer the existing register action) and Kuma monitors matching no fleet site (listed, ignored; they're not SpinupTUI's business).
5. Write the rebuilt registry to local config, then do one `incidents --all` dry run to prove Sentinel now sees the fleet.

**Invariants:**

- **Attach is read-only toward Kuma and the servers.** It never creates, renames or edits a monitor, and above all **never generates a new push token**. The server-side crons are already pushing to the existing tokens; a new token would silently break them.
- **Re-runnable.** Attach again after adding monitors elsewhere, and it only fills gaps. This also covers drift, when a monitor was deleted directly in Kuma.

**A sturdier key than names (later).** Names can be edited in Kuma's UI. Kuma supports tags, so SpinupTUI could tag every monitor it creates (`spinuptui` = `{domain}:{kind}`) and match on tags first, names second. Back-tagging existing monitors during attach would be a write to Kuma, so it's an opt-in, confirm-gated step, not part of the read-only attach.

#### Bootstrap: no Kuma yet

**The constraint that decides where Kuma lives.** Push monitors (load, Redis, PHP-fatal) work by the *servers* calling Kuma every minute, so Kuma must be reachable from the public internet. It also shouldn't share fate with what it watches: not on a fleet server (that server's outage silences its own alarms), and ideally not on the home station (a home internet outage would page "everything down", and the station heartbeat from idea 2 would be reporting to itself).

**Decided 2026-10-15: Kuma runs on a small dedicated server.** It's its own thing, separate from both the fleet and the station. That's also how the existing production Kuma is run. Tunnel-on-the-station is dropped as an option, and bring-your-own Kuma (connect by URL, then attach) stays supported as it is today. The bootstrap is a Sentinel feature with Samurai supplying the nginx side: Sentinel owns "you need a Kuma, let's build one", and Samurai's gated nginx deploy ships the reverse-proxy config.

#### The dedicated Kuma server, step by step

Built from pieces SpinupTUI mostly has already:

1. **Create the server** through SpinupWP (the existing `c` flow), at the smallest size. **Prefer a different provider or region from the fleet**, so a provider or region outage can't take the fleet and its monitor down together. That's the same don't-share-fate logic, one level up.
2. **Create the site** at its hostname with DNS and HTTPS (the existing `V` wizard's DNS → propagate → blank site → Let's Encrypt steps). It's a blank site that will never run WordPress.
3. **Install Kuma** (needs sudo, which SpinupTUI already handles), at a pinned version, supervised so it restarts on reboot, and **bound to `127.0.0.1:3001` only**. If Kuma runs in Docker, this matters doubly: published Docker ports bypass the host firewall, so a port bound to all interfaces would put Kuma's raw port on the internet.
4. **Ship the reverse proxy** (Samurai, through nginx-deploy): WebSocket upgrade headers, `proxy_pass` to the local port, and the ACME challenge routed to SpinupWP's shared certbot webroot.
5. **First-run Kuma:** create the admin account through Kuma's setup socket event, store the credentials, and connect SpinupTUI.
6. **Wire alerts:** create Kuma's Telegram notification provider from Beacon's credentials.
7. **Register monitors** fleet-wide (one confirm listing every domain), plus the station's heartbeat.
8. **Prove it:** a test notification from Kuma and an `incidents --all` that sees the fleet.

**Lessons the existing Kuma server already paid for**, which the recipe must encode:

- **SpinupWP's static-file and page-cache includes break a reverse proxy.** The site's main config normally pulls in `server/*`, whose regex `location` blocks for `.css`/`.js`/`.png` and FastCGI cache rules intercept requests meant for Kuma. The existing fix edits the SpinupWP-managed main config to drop that include. But nginx-deploy's whole model is that SpinupWP's files stay SpinupWP's, since it can regenerate them (a dashboard HTTPS toggle, a server update) and silently restore the include. **Open question: can the proxy be expressed entirely in allowlisted custom files?** A candidate is a `location ^~ /` block, because `^~` prefix matches win over regex locations. It conflicts with a `location /` that the main config may already define, so it needs testing on a scratch server. If it can't be done that way, Samurai needs a "managed file was regenerated" drift alert for this site specifically.
- **Let's Encrypt renewal failed once.** The challenge has to be served from SpinupWP's shared `/sites/.certbot` webroot (by including SpinupWP's own `well-known.conf`), not the site's own `files/`, which nginx can't write to. Renewal can be tested safely with `certbot renew --dry-run`.

#### Who watches Kuma?

A dedicated Kuma is a single point of silence: if it dies, nothing pages. The station closes the loop. Kuma watches the station (the heartbeat push monitor), and **Sentinel on the station watches Kuma**: each tick confirms Kuma is reachable and its socket answers, and on failure it pages through Beacon, a path that doesn't depend on Kuma. Two independent machines, each watching the other.

Also on the checklist for the Kuma server: **back up Kuma's data** (its SQLite database holds every monitor, push token and history; losing it means re-registering everything and re-pointing every server cron), and a deliberate **upgrade path** (pinned version, tested against SpinupTUI's socket client before bumping).

#### Open questions

- **Kuma alerts vs Beacon alerts.** Kuma pages on its own; Sentinel pages via Beacon after triage. Is that one alert or two for the same incident? A reasonable split: Kuma for the raw "it's down" (fast, no dependency on the station), Beacon for the triaged "here's why" (slower, richer). Worth stating explicitly so it doesn't feel like duplicate noise.
- Does bootstrap belong to Sentinel or to station setup? Sentinel owns the logic and station setup calls it, the same as with every other module.
- Fleet-wide registration creates monitors on client sites. Today that's per-site and deliberate. A one-pass "monitor everything" needs a clear confirm step listing every domain.

### 4. Integration plan: bringing the existing pieces in

All four modules already exist as working private tooling outside this repo: an incident-watch and diagnostics workspace (Sentinel), the nginx-deploy pipeline (Samurai), a git-backed job runner (Scheduler), and Telegram/Basecamp notification code spread across those and other always-on scripts (Beacon). Station setup is the only piece with no prior art. The plan is to incorporate the four into SpinupTUI first, then build station setup on top.

**Extract the engine; leave the repo.** The existing repos hold things that can never enter this public repo: per-site incident histories, client config, machine-specific launchd plists, client thread IDs. So incorporating a module means moving its reusable *engine* into `spinuptui`, while the private repo stays as a *user* of it. The diagnostics workspace keeps being the incident archive and investigation playbook, and calls Sentinel the way it already calls `ssh-exec` and `incidents`. The same goes for the others. Every extracted engine gets the public-framework/private-data split from idea 1: example configs committed, real ones never.

**Beacon first, because it's already duplicated.** At least four separate scripts each carry their own copy of "send a Telegram message with this bot token and chat ID". Collapsing them into one `spinuptui beacon send` is the smallest useful step, and it proves the module pattern before anything bigger.

**One clock: Scheduler's dispatcher is the only OS-level scheduled unit.** Today each piece installs its own launchd job (the incident watcher, its watchdog, the 08:00 digest, the job runner's 5-minute tick). If the four modules arrive before a shared install model, we'd build four install stories and then replace them with station setup. Instead, Scheduler's dispatcher becomes the single OS unit, and everything recurring is a Scheduler job: Sentinel's ticks (every 10 minutes today, which a 5-minute tick covers), the daily digest, Samurai's ban expiries. That pays off three ways:

- Station setup installs one unit per OS (launchd or systemd), not one per module.
- Hard-won scheduler lessons (launchd `StartInterval` agents wedging, so fixed calendar times are used instead; the bare PATH under launchd) are solved once, in one place.
- "Is the station alive?" becomes one question: is the dispatcher still ticking? The station heartbeat is just a Scheduler job that pings Kuma.

**Define the module contract before the first module ships.** Each module declares its config section, its state directory, its Scheduler jobs, its dependencies, and a `status` check. Beacon is the first to implement it, and the Modules screen (idea 2) is a view over these declarations.

### 5. Playbook retired; "station" is the concept

Decided 2026-10-16. Playbook kept proving useful in design sessions, but on inspection it bundled three different things, and none of them needs a product name:

1. **How modules plug in** (the module contract, dependency resolution). This is internal architecture, the orchestration layer of SpinupTUI. Users meet it as the Modules screen and the install button.
2. **Preparing a fresh machine** (host checks, SSH key, Kuma attach, self-test). This is a one-time action, and with Scheduler as the only clock (idea 4) most of it belongs to the modules: staying awake, the bare PATH under launchd, and reboot survival are Scheduler's requirements; Kuma attach and the SSH key are Sentinel's setup; the test message is Beacon's. Turning on Scheduler is effectively what makes a machine a station, since a laptop that sleeps can't keep a schedule.
3. **The machine's ongoing role** (this box watches the fleet). This is the only one that persists, and it's the one worth naming: a **station**. You check a station's status, run its doctor, and see "Sentinel runs on *station*, last heartbeat 3 min ago".

What remains is a shortcut, **"Set up this machine as a station"** (`spinuptui station setup`), that turns on all four modules in dependency order. It's a button and a command, not a fifth product.

Why not keep the name: every module answers "what does it do for me?" (watches, defends, tells you, remembers). Playbook's answer is "it installs the others", which is a step towards a feature, not a feature. Naming by outcome ("Runs headless", "Set up as a station") teaches itself, while a metaphor has to be learned first. Retiring it also clears the overlap with the diagnostics workflow, which was already informally called a playbook.

When to revisit: if headless operation ever becomes its own offering (a preconfigured station people download or buy), the setup *is* the product and would deserve a brand.
